### Severity and Priority Definitions

**Severity** describes impact if exploited or if the issue manifests:

- **Critical**: Likely to enable account compromise, credential disclosure, arbitrary file access, SSRF to internal services, or severe availability degradation.
- **High**: Material security hardening gap or a reliability issue that can plausibly become an outage in production.
- **Medium**: Meaningful quality/perf/maintainability concern with operational risk, but not an immediate “break glass” item.
- **Low**: Best-practice improvements, tooling, or “nice to have” hardening.

**Priority** describes recommended resolution ordering (independent of effort):

- **P0**: Fix first; avoid deploying externally without these addressed (or explicitly mitigated).
- **P1**: Fix next; high operational value and reduces ongoing risk.
- **P2**: Fix after P0/P1; improves robustness, maintainability, and long-term velocity.
- **P3**: Opportunistic; address when touching nearby code or when standardizing practices.

### P0-01: Passwords appear to be stored with reversible encryption (not one-way hashing)

- **Severity:** Critical
- **Primary evidence (code):**
  - `src/Melodee.Common/Utility/EncryptionHelper.cs` implements reversible AES encryption/decryption (`Encrypt`/`Decrypt`) using `CipherMode.CBC` without authentication.
  - `src/Melodee.Common/Services/UserService.cs` contains logic comparing encrypted values and decrypting stored password material (`PasswordEncrypted`, `Decrypt(...)`).
- **Why this matters:**
  - If the encryption key material is compromised (configuration leak, memory dump, insider threat, backup exposure), all user passwords become recoverable (unlike password hashes, which are intentionally slow and non-reversible).
  - AES-CBC without authentication is malleable; ciphertext integrity is not guaranteed. Even if the key remains secret, unauthenticated encryption is not appropriate for storing passwords.
- **Recommended corrective actions:**
  1. **Stop decrypting passwords entirely.** Authentication should verify a password against a one-way hash (`Verify(password, storedHash)`), never by decrypting stored secrets.
  2. **Migrate to a password hashing scheme** suitable for user authentication:
     - Prefer ASP.NET Core Identity’s password hasher (`IPasswordHasher<TUser>`) or a dedicated KDF such as Argon2id (preferred) or BCrypt (acceptable).
     - Store only: algorithm identifier + parameters (cost) + salt + derived hash.
  3. **Design a safe migration path** for existing users:
     - Option A (preferred): force password reset (invalidate old password material; email reset flow).
     - Option B: opportunistic migration on next successful login (verify using legacy method once; immediately re-hash and overwrite with a proper password hash).
     - Either way: remove legacy support (`enc:` prefix patterns) once the migration window closes.
  4. **Audit all places where `PasswordEncrypted` is used**, including API auth flows and OpenSubsonic compatibility endpoints, to ensure no path still relies on decrypting passwords.
- **Verification (tests / checks):**
  - Add tests ensuring no code path can obtain plaintext passwords (no `Decrypt` usage in auth).
  - Add tests verifying password hashes change when cost factors change (rehash policy).
  - Add a security regression test ensuring login verifies via hash only.
- **Mentioned in reviews:**
  - `design/reviews/20260113.minimaxm2.md`

### P0-02: JWT validation is configured to skip issuer/audience validation

- **Severity:** Critical
- **Primary evidence (code):**
  - `src/Melodee.Blazor/Services/AuthService.cs` sets:
    - `ValidateIssuer = false`
    - `ValidateAudience = false`
- **Why this matters:**
  - Tokens can be accepted without verifying they were minted for this application and intended audience. If a signing key leaks (or is shared across environments), token forgery and cross-environment token reuse become much easier.
  - Disabling issuer/audience validation is a common cause of “works locally” auth that becomes exploitable in production.
- **Recommended corrective actions:**
  1. **Define issuer and audience values** (per environment) in configuration (e.g., `MelodeeAuthSettings:Issuer`, `MelodeeAuthSettings:Audience`).
  2. **Enable validation** in token validation parameters:
     - `ValidateIssuer = true`, `ValidIssuer = ...`
     - `ValidateAudience = true`, `ValidAudience = ...` (or `ValidAudiences`)
     - Keep `ValidateIssuerSigningKey = true` and `ValidateLifetime = true` (ensure lifetime validation is enabled if not already).
  3. **Fail closed** when required values are missing:
     - Startup-time validation: refuse to boot if issuer/audience are absent in non-development environments.
  4. **Add minimum JWT signing key requirements**:
     - Validate the configured key length (and encoding) at startup.
     - Prefer per-environment keys and rotation policies.
- **Verification (tests / checks):**
  - Unit tests covering: wrong issuer rejected, wrong audience rejected, expired token rejected, missing issuer/audience fails validation.
  - Integration test hitting a protected endpoint with a token minted for a different issuer/audience.

### P0-03: Browser storage of JWTs in `localStorage` increases XSS blast radius

- **Severity:** High (often Critical depending on threat model)
- **Primary evidence (code):**
  - `src/Melodee.Blazor/Services/AuthService.cs` reads/writes JWTs to `ILocalStorageService` (`melodee_auth_token`).
- **Why this matters:**
  - Any XSS in the app (or a third-party script compromise) can read `localStorage` and exfiltrate tokens, enabling account takeover.
  - Blazor Server typically relies on server-side session + auth cookies; a client-stored JWT is a deliberate trade-off that should be justified and hardened.
- **Recommended corrective actions:**
  1. Prefer **HttpOnly + Secure cookies** for session/auth state so client-side scripts cannot read tokens.
  2. If JWT-in-browser is required (e.g., for specific clients), reduce exposure:
     - Store in **memory** only where possible.
     - Ensure short expirations, refresh token rotation, and strict CSP.
  3. Ensure token timestamps use UTC:
     - `expires: DateTimeOffset.UtcNow.AddHours(...)` (avoid `DateTime.Now`).
  4. Ensure tokens include `iss`, `aud`, `nbf`, and required claims; consider `jti` + revocation strategy.
- **Verification (tests / checks):**
  - Security review for XSS sinks; ensure CSP is strong enough for the chosen approach.
  - If cookies are used: verify `HttpOnly`, `Secure`, `SameSite`, and anti-CSRF strategy.
- **Mentioned in reviews:**
  - `design/reviews/20260113.gpt52codexhigh.md`

### P0-04: CORS is configured as “allow everything” in the runtime pipeline

- **Severity:** Critical (when combined with cookie auth, bearer tokens, or sensitive endpoints)
- **Primary evidence (code):**
  - `src/Melodee.Blazor/Program.cs` calls `app.UseCors(...)` with:
    - `.AllowAnyOrigin()`
    - `.AllowAnyMethod()`
    - `.AllowAnyHeader()`
- **Why this matters:**
  - If any endpoints rely on cookies or implicit credentials, permissive CORS can enable cross-origin abuse and token leakage patterns.
  - Even if credentials are not allowed, the broad policy increases attack surface and makes security posture unclear across environments.
- **Recommended corrective actions:**
  1. Replace the inline policy with **named policies** and explicit allowed origins.

  3. Avoid `AllowAnyOrigin` when using credentials; use `WithOrigins(...).AllowCredentials()` with an allowlist.
  4. Add automated tests (or startup validation) ensuring production configuration does not enable wildcard origins.
- **Verification (tests / checks):**
  - Integration test verifies disallowed origin does not receive `Access-Control-Allow-Origin`.
  - Confirm websocket/SignalR connections are unaffected (if used) and correctly restricted.

### P0-05: Path traversal risk when loading email templates by language code

- **Severity:** Critical (arbitrary file read within template library path)
- **Primary evidence (code):**
  - `src/Melodee.Blazor/Services/Email/EmailTemplateService.cs`:
    - `NormalizeLanguageCode(...)` lowercases but does not reject path separators or `..`.
    - `LoadTemplateFromLibraryAsync($"{normalizedLanguage}/PasswordReset.html")` uses `Path.Combine(libraryPath, relativeTemplatePath)` without canonicalization/containment checks.
    - Exceptions are swallowed (`catch { return null; }`), which can conceal exploitation attempts.
- **Why this matters:**
  - If `languageCode` can be influenced by a user (directly or indirectly), an attacker can attempt `../../...` traversal and read arbitrary files under the Templates library root (and sometimes beyond, depending on how paths are combined and normalized on the OS/filesystem).
  - Email templates are often used in security-sensitive flows (password reset); making them file-read gadgets is a serious risk.
- **Recommended corrective actions:**
  1. Treat `languageCode` as untrusted input unless proven otherwise.
  2. Implement a strict allowlist:
     - Only allow known supported cultures (the same list used by request localization, or a dedicated config list).
     - Reject any language code containing `Path.DirectorySeparatorChar`, `Path.AltDirectorySeparatorChar`, or `..`.
  3. Enforce path containment:
     - Compute `fullPath = Path.GetFullPath(Path.Combine(root, relative))`.
     - Verify `fullPath` starts with `rootFullPath + Path.DirectorySeparatorChar` (or use a robust “is under root” helper).
  4. Don’t swallow exceptions silently:
     - Log at least a warning with a sanitized path and correlation ID.
- **Verification (tests / checks):**
  - Unit test: passing `../` in language code must be rejected (and must not probe the filesystem).
  - Unit test: supported culture loads expected template file.
- **Mentioned in reviews:**
  - `design/reviews/20260113.gpt52codexhigh.md`

### P0-06: Unconstrained file system operations can enable destructive path abuse

- **Severity:** Critical (potential arbitrary delete/move if user-controlled paths reach these methods)
- **Primary evidence (code):**
  - `src/Melodee.Common/Services/FileSystemService.cs` exposes operations like `Directory.Delete`, `File.Delete`, `Directory.Move` without visible root/containment checks.
  - Multiple reviews call out “path guarding” gaps in file move/delete flows.
- **Why this matters:**
  - Even if paths are intended to be internal, file-path bugs routinely become security bugs as features evolve (uploads, library paths, plugins, templates, metadata).
  - A single missing canonicalization step can turn “delete album art” into “delete arbitrary file on server”.
- **Recommended corrective actions:**
  1. Introduce an explicit “allowed roots” concept:
     - Library root(s), temp root, cache root, templates root, etc.
  2. Centralize path normalization and validation:
     - `GetFullPath`, reject relative paths, and enforce “under root” containment.
  3. Add guardrails for dangerous ops:
     - Refuse to delete/move the root directory itself.
     - Require explicit flags for recursive deletes and log them.
  4. Ensure user-facing endpoints never accept raw paths:
     - Use opaque IDs and server-side resolution to paths.
- **Verification (tests / checks):**
  - Unit tests for the path guard helper:
    - Rejects `..`, absolute paths outside root, mixed separators, and symlink escapes (if applicable).
  - Integration test around any endpoint that triggers deletion/move behavior.

### P0-07: SSRF and resource exhaustion risk when fetching arbitrary external URLs

- **Severity:** Critical
- **Primary evidence (reviews + code references):**
  - Reviews identify external fetches in `src/Melodee.Common/Services/Extensions/HttpClientFactoryExtensions.cs` as lacking allowlists, timeouts, and size limits.
  - General SSRF hardening is called out across multiple reviews, even where a validator exists elsewhere.
- **Why this matters:**
  - SSRF can reach internal services (cloud metadata endpoints, internal admin panels, loopback-only services) and is frequently used to pivot to credential theft.
  - Without size limits, attackers can force memory/disk/network exhaustion (download very large payloads, slow responses, decompression bombs).
- **Recommended corrective actions:**
  1. Implement **scheme and host validation** for outbound requests:
     - Allow only `https` (and possibly `http` only if strictly needed).
     - Deny loopback, private IP ranges, link-local, and metadata endpoints.
     - Prefer an allowlist of known domains where feasible (e.g., image CDNs, metadata providers).
  2. Enforce **timeouts** and **max response sizes**:
     - `HttpClient.Timeout` plus per-request cancellation token.
     - Limit content length; stop reading after a cap (even if server lies about headers).
  3. Disable or restrict redirects:
     - `AllowAutoRedirect = false` or validate each redirect hop.
  4. Log outbound fetch failures with sanitized targets and correlation ID.
- **Verification (tests / checks):**
  - Unit tests for SSRF validator/URL normalization (private IP, localhost, redirect-to-private).
  - Integration tests using a local test server to simulate large payloads and redirect chains.

### P0-08: Regex evaluation can still hang (ReDoS) despite a “guard” abstraction

- **Severity:** Critical (availability; can become security-impacting)
- **Primary evidence (code):**
  - `src/Melodee.Mql/Security/MqlRegexGuard.cs` uses `Task.Run(...).Result` and constructs a `Regex` inside the task without a timeout:
    - `var regex = new Regex(..., RegexOptions.Compiled);`
  - Cancellation tokens do not reliably interrupt catastrophic regex evaluation; `Task.Run` does not make `Regex.Match` cancellable.
- **Why this matters:**
  - A crafted pattern and input can trigger catastrophic backtracking and pin CPU threads for long periods, leading to request starvation and denial of service.
  - Blocking on `task.Result` can also introduce deadlocks and thread-pool starvation under load.
- **Recommended corrective actions:**
  1. Construct regexes with a timeout:
     - `new Regex(pattern, options, timeout)`
  2. Consider `RegexOptions.NonBacktracking` (where behavior is acceptable), especially for untrusted patterns.
  3. Remove `Task.Run` + `.Result` pattern:
     - Execute regex match directly with a timeout-enabled regex.
     - If isolation is required, consider a dedicated worker with bounded concurrency rather than spinning tasks per request.
  4. Decide policy for untrusted patterns:
     - Reject patterns that include known “evil regex” constructs if the language permits it.
- **Verification (tests / checks):**
  - Add regression tests with known catastrophic patterns and confirm evaluation reliably times out.
- **Mentioned in reviews:**
  - `design/reviews/20260113.gpt52codexhigh.md`

### P1-01: Host header trust and sync-over-async in base URL resolution

- **Severity:** High
- **Primary evidence (code):**
  - `src/Melodee.Blazor/Services/BaseUrlService.cs`:
    - Blocks on async configuration: `_configurationFactory.GetConfigurationAsync().GetAwaiter().GetResult()`
    - Falls back to `httpContext.Request.Host.Value` when `SystemBaseUrl` is missing.
- **Why this matters:**
  - **Host header injection**: if base URLs are used in externally consumed content (emails, redirects), attackers can poison links (phishing/open redirect).
  - **Sync-over-async**: blocking can cause thread starvation and hard-to-debug stalls; it also increases tail latency.
- **Recommended corrective actions:**
  1. Require a configured base URL for any externally generated URL (password reset, invites).
  2. If a fallback is needed:
     - Validate host against an allowlist (or use ASP.NET Core’s forwarded headers + known proxies and host filtering).
  3. Make base URL resolution async:
     - Cache configuration results and avoid `.GetResult()` on request paths.
- **Verification (tests / checks):**
  - Unit test: when `SystemBaseUrl` is absent, service refuses to generate external links (or validates host allowlist).
  - Concurrency test: base URL resolution does not block under load.
- **Mentioned in reviews:**
  - `design/reviews/20260113.gpt52codexhigh.md`

### P1-02: `async void` event handlers hide exceptions and can crash the process

- **Severity:** High
- **Primary evidence (code):**
  - `src/Melodee.Common/Services/SearchEngines/ArtistSearchEngineService.cs` defines `private async void OnConfigurationChanged(...)`.
  - `src/Melodee.Blazor/Components/Layout/MainLayout.razor` defines `private async void OnConfigurationChanged(...)`.
- **Why this matters:**
  - `async void` exceptions can bypass normal error handling and crash the app, and the caller cannot await completion.
  - Configuration change handlers are usually cross-cutting and can be triggered at unexpected times.
- **Recommended corrective actions:**
  1. Convert to a fire-and-forget pattern with explicit exception handling:
     - `private void OnConfigurationChanged(...) => _ = HandleConfigurationChangedAsync();`
     - `private async Task HandleConfigurationChangedAsync() { try { ... } catch (Exception ex) { ... } }`
  2. Ensure handlers are unsubscribed appropriately to avoid leaks.
  3. Where ordering matters, serialize config-change processing via a single-flight mechanism.
- **Verification (tests / checks):**
  - Unit/integration test: configuration change does not crash and logs failures.
- **Mentioned in reviews:**
  - `design/reviews/20260113.gpt41.md`
  - `design/reviews/20260113.claudeopus45.md`

### P1-03: Blocking async calls (`.Result`, `.Wait()`, `GetAwaiter().GetResult()`) can deadlock and degrade throughput

- **Severity:** High
- **Primary evidence:**
  - Multiple reviews report `.Result` usage in filters/jobs/commands and other request-adjacent paths.
  - `BaseUrlService` is a concrete example of sync-over-async.
- **Why this matters:**
  - Blocking calls can tie up thread-pool threads, causing cascading latency and, in some contexts, deadlocks.
  - In Blazor Server, long-running blocking work can degrade user sessions (SignalR circuit responsiveness).
- **Recommended corrective actions:**
  1. Adopt “async all the way” in request processing and background jobs.
  2. Where a truly synchronous boundary exists (rare), isolate it to startup/entry points and document why blocking is safe.
  3. Add analyzers or CI checks to flag sync-over-async patterns in server projects.
- **Verification (tests / checks):**
  - Static analysis (Roslyn analyzer or grep-based CI gate).
  - Load test: ensure no thread-pool starvation under typical concurrency.
- **Mentioned in reviews:**
  - `design/reviews/20260113.claudeopus45.md`

### P1-04: Memory and I/O spikes in image merge/CRC computation (unbounded parallel `ReadAllBytesAsync`)

- **Severity:** High
- **Primary evidence (code):**
  - `src/Melodee.Common/Services/ServiceBase.cs` reads all files into memory and uses `Task.WhenAll`, potentially processing many large images concurrently.
- **Why this matters:**
  - Large albums or large libraries can cause sudden memory spikes, increased GC pressure, and disk contention.
  - This risk compounds under concurrent operations (multiple users, jobs, scans).
- **Recommended corrective actions:**
  1. Replace full-buffer reads with streaming:
     - Compute CRC/hash via `Stream` and incremental update.
  2. Bound concurrency:
     - Use `Parallel.ForEachAsync` with `MaxDegreeOfParallelism`, or a `SemaphoreSlim`.
  3. Consider file size thresholds and early exits to avoid processing massive files unexpectedly.
  4. Measure and add perf tests around “merge images” for large directories.
- **Verification (tests / checks):**
  - Benchmark scenario: many images, large images, concurrent merges.
  - Memory profiling test (or at least a stress test in CI on a schedule).

### P1-08: File upload and content handling need explicit “defense in depth” controls

- **Severity:** High
- **Primary evidence:**
  - Reviews flag missing malware scanning/content validation and recommend multi-layer validation for file upload endpoints and other content ingestion points.
- **Why this matters:**
  - Upload endpoints are a common entry point for:
    - storage abuse (very large files)
    - malicious payloads (polyglots, disguised executables)
    - downstream vulnerabilities (image parsers, tag parsers)
  - Even if Melodee primarily manages local libraries, “any content ingestion” (images, metadata, templates) benefits from strict controls.
- **Recommended corrective actions:**
  1. Validate at multiple layers:
     - request size limits, content-type checks, file extension allowlists (not sufficient alone), and “magic bytes” sniffing for common formats.
  2. Store uploads safely:

### P3-05: Async “micro-optimizations” (e.g., blanket `ConfigureAwait(false)`) should be applied intentionally

  3. Consider analyzers:
     - Either enforce a consistent policy per project (server vs. library) or avoid enforcing it entirely.
- **Verification (tests / checks):**
